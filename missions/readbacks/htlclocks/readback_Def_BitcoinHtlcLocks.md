# Read-back: definitions in `Def_BitcoinHtlcLocks`

This file introduces two definitions and no theorems.

## `BitcoinHtlcLocks.RevocationSpend`

A proposition $\mathrm{RevocationSpend}(c, \mathit{script}, r, \mathit{pk}, \mathit{sig})$ in five arguments: a *verification context* $c$ and four byte strings (finite lists of 8-bit vectors) $\mathit{script}$, $r$ (`revHash`), $\mathit{pk}$ and $\mathit{sig}$. The context $c$ is a record $(c.\mathrm{flags}, c.\mathrm{tx}, c.\mathrm{nIn}, c.\mathrm{amount})$ where $c.\mathrm{flags}$ is a record of seven Booleans $(\mathrm{p2sh}, \mathrm{witness}, \mathrm{taproot}, \mathrm{dersig}, \mathrm{cltv}, \mathrm{csv}, \mathrm{nulldummy})$, $c.\mathrm{tx}$ is a transaction (a record with a version $\in \mathbb{N}$, a list of inputs, a list of outputs, and a lock time $\in \mathbb{N}$; each input having a previous outpoint, a `scriptSig` byte string, a sequence number $\in \mathbb{N}$ and a witness stack), $c.\mathrm{nIn} \in \mathbb{N}$ is an input index and $c.\mathrm{amount} \in \mathbb{Z}$ is an amount. The proposition is the conjunction of two conditions:

$$\mathrm{hash160}(\mathit{pk}) = r \qquad\text{and}\qquad \mathrm{checkSigPreTapscript}\big(\mathrm{sigFlagsOf}(c.\mathrm{flags}),\ c.\mathrm{tx},\ c.\mathrm{nIn},\ c.\mathrm{amount},\ \mathrm{witnessV0},\ \mathit{script},\ \mathit{sig},\ \mathit{pk}\big) = \mathrm{some}\ \mathbf{true}.$$

Here $\mathrm{hash160}(m) = \mathrm{ripemd160}(\mathrm{sha256}(m))$ with concrete SHA-256 and RIPEMD-160 implementations, so the first conjunct says the 20-byte RIPEMD-160-of-SHA-256 digest of $\mathit{pk}$ equals $r$ as byte strings (nothing requires $r$ to have length 20; if it does not, the equality is simply false). $\mathrm{sigFlagsOf}(F)$ is the signature-flag record $(\mathrm{dersig} = F.\mathrm{dersig}, \mathrm{lowS} = \mathbf{false}, \mathrm{strictenc} = \mathbf{false}, \mathrm{witnessPubkeyType} = \mathbf{false})$. $\mathrm{checkSigPreTapscript}$ returns an optional Boolean: with signature version $\mathrm{witnessV0}$ the script code is $\mathit{script}$ unchanged (no find-and-delete of the signature push, which only happens for the base version); it returns *no value* when the signature-encoding check fails (with these flags: an empty $\mathit{sig}$ passes; otherwise, if $c.\mathrm{flags}.\mathrm{dersig}$ holds and $\mathit{sig}$ is not a valid DER-encoded signature it fails; otherwise it passes) or the public-key-encoding check fails (with $\mathrm{strictenc}$ and $\mathrm{witnessPubkeyType}$ both off it never fails); otherwise it returns $\mathrm{some}$ of $\mathrm{checkECDSASignature}(c.\mathrm{tx}, c.\mathrm{nIn}, c.\mathrm{amount}, \mathrm{witnessV0}, \mathit{sig}, \mathit{pk}, \mathit{script})$, which is **false** if $\mathit{pk}$ is not a valid public key, **false** if $\mathit{sig}$ is empty, and otherwise splits $\mathit{sig}$ into its last byte (the hash type) and the remaining raw signature, computes the witness-version-0 signature hash of $(\mathit{script}, c.\mathrm{tx}, c.\mathrm{nIn}, \text{hash type}, c.\mathrm{amount})$, returns **false** if $c.\mathrm{amount} < 0$, and otherwise returns the outcome of verifying the raw signature against that hash under $\mathit{pk}$. Thus the second conjunct requires the encoding checks to pass *and* the ECDSA verdict to be true; a "no value" result or a false verdict both make the proposition false. Nothing in the definition refers to $c.\mathrm{flags}.\mathrm{witness}$, $\mathrm{cltv}$, or the other flags, to the witness stacks of $c.\mathrm{tx}$, or to any bound on $c.\mathrm{nIn}$ (an out-of-range $c.\mathrm{nIn}$ is passed through to the signature-hash computation as is). The byte string $\mathit{script}$ is used only as the script code for the signature hash.

## `BitcoinHtlcLocks.HeightLocked`

A proposition $\mathrm{HeightLocked}(tx)$ in one argument, a transaction $tx$ (a record with a version $\in \mathbb{N}$, a list of inputs, a list of outputs and a lock time $\mathrm{nLockTime}(tx) \in \mathbb{N}$). It is the conjunction

$$0 < \mathrm{nLockTime}(tx) \;\wedge\; \mathrm{nLockTime}(tx) < \mathrm{LOCKTIME\_THRESHOLD}, \qquad \mathrm{LOCKTIME\_THRESHOLD} = 500\,000\,000,$$

both comparisons on natural numbers. Equivalently, $1 \le \mathrm{nLockTime}(tx) \le 499\,999\,999$. The proposition is false when $\mathrm{nLockTime}(tx) = 0$ and false when $\mathrm{nLockTime}(tx) \ge 500\,000\,000$. It says nothing about the transaction's inputs, their sequence numbers, its outputs or its version, and places no upper bound such as $2^{32}$ on the lock time beyond the threshold itself.
