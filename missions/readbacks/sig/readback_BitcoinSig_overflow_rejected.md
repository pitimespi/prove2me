# Read-back: `BitcoinSig.overflow_rejected`

**Binders and hypothesis.** Universally quantified over three byte strings $pk$, $hash$, $sig$, with one hypothesis $h$: `parseDerLax` $sig$ = some $(0, 0)$. That is, the lax DER parser does *not* reject $sig$ structurally (the result is not "none"), and the pair it returns is $(0,0)$.

**How the hypothesis can arise.** Per the definition of `parseDerLax`, the pair $(0,0)$ is produced in exactly these situations after the structural phase succeeds (sequence tag `0x30`, a sequence-length byte whose long-form length bytes — if any — are skipped unread, two integers each with tag `0x02` and a short or long-form length that fits within the input, trailing bytes ignored): (a) after stripping leading zero bytes, the $R$ integer or the $S$ integer still has more than 32 bytes; or (b) both fit in 32 bytes but the big-endian value of $R$ or of $S$ is $\geq n$; or (c) both integers genuinely have value $0$ (for example zero-length integers, or integers consisting only of zero bytes). The hypothesis does not distinguish these cases.

**Conclusion.**
$$\text{pubkeyVerify}\ pk\ hash\ sig = \text{false}.$$

**Unfolding.** `pubkeyVerify` $pk\,hash\,sig$ is: false if `pubkeyValid` $pk$ is false (first byte does not announce the actual length); false if `parsePubkey` $pk$ is "none" (not a valid compressed/uncompressed/hybrid point); false if `parseDerLax` $sig$ is "none"; otherwise, with $Q$ the parsed point and $(r,s)$ the parsed pair, `ecdsaVerifyRaw` (some $Q$) (`beVal` $hash \bmod n$) $r$ (`normalizeS` $s$). Under $h$, $(r,s) = (0,0)$, `normalizeS` $0 = 0$, and `ecdsaVerifyRaw` begins with "if $r = 0$ or $s = 0$ or $r \geq n$ or $s \geq n$ then false", which fires. So every branch of `pubkeyVerify` yields false, whatever $pk$ and $hash$ are — including a perfectly valid key and any message bytes (which have no length constraint and are read big-endian modulo $n$).

**What is not said.** The statement does not say that signatures with over-long or overflowing integers are rejected by the *encoding* checks (`isValidSignatureEncoding`, `checkSignatureEncoding`) — it concerns only `pubkeyVerify`. It does not say what `checkLowS` returns on such a signature (by the definition it returns true, since $s = 0$ is not high, but that is not part of this statement). It does not say anything about signatures for which `parseDerLax` returns "none" (also false in `pubkeyVerify`, but not asserted here) or returns some other pair. It does not say that $(0,0)$ arises *only* from overflow; a signature honestly encoding $r = s = 0$ also satisfies the hypothesis and is covered. It does not mention `checkECDSASignature` or the hash-type byte: $sig$ here is the DER body as passed to `pubkeyVerify`, without any trailing hash-type byte being stripped.
