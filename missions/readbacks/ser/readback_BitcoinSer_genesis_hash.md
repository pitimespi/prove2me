# Read-back: `BitcoinSer.genesis_hash`

**Binders and hypothesis.** None. This is a closed statement about two concrete byte strings; there are no variables and no assumptions.

**Conclusion.** The header hash of the file's constant `genesisHeader` equals the file's constant 32-byte list `genesisHash`:
$$\texttt{headerHash}(\texttt{genesisHeader}) = \texttt{genesisHash}.$$

**Unfolding the left side.** $\texttt{headerHash}(h) = \texttt{hash256}(\texttt{serHeader}(h)) = \texttt{sha256}(\texttt{sha256}(\texttt{serHeader}(h)))$ — the file's SHA-256 applied twice to the serialized header. The constant `genesisHeader` is the record with: version $1$ (as a signed integer); previous-block field equal to 32 zero bytes; merkle-root field equal to $\texttt{txid}(\texttt{genesisCoinbase})$, i.e. the double-SHA-256 of the witness-free serialization of the constant coinbase transaction (version $1$; one input with outpoint (32 zero bytes, $\mathrm{0xffffffff}$), the 77-byte `genesisScriptSig`, sequence $\mathrm{0xffffffff}$, empty witness; one output of value $5\,000\,000\,000$ with the 67-byte `genesisOutputScript`; lock time $0$); time $1231006505$; bits $\mathrm{0x1d00ffff}$; nonce $2083236893$. Its serialization $\texttt{serHeader}$ is the 80-byte string
$$\texttt{serInt32}(1) \mathbin{+\!\!+} 0^{32} \mathbin{+\!\!+} \texttt{txid}(\texttt{genesisCoinbase}) \mathbin{+\!\!+} \texttt{ser32}(1231006505) \mathbin{+\!\!+} \texttt{ser32}(\mathrm{0x1d00ffff}) \mathbin{+\!\!+} \texttt{ser32}(2083236893),$$
with all integers little-endian. Note that the merkle-root slot is a *computed* value: the statement implicitly involves the correctness of the whole transaction serializer and of the SHA-256 implementation on the 204-byte coinbase serialization, and then of SHA-256 again on the 80-byte header — four SHA-256 evaluations in all, each on inputs of one or more 64-byte padded chunks (the 204-byte message pads to 256 bytes, i.e. 4 chunks; the 80-byte header pads to 128 bytes, 2 chunks; each 32-byte intermediate pads to 1 chunk).

**Unfolding the right side.** `genesisHash` is the literal 32-byte list $[\mathrm{6f}, \mathrm{e2}, \mathrm{8c}, \mathrm{0a}, \mathrm{b6}, \mathrm{f1}, \mathrm{b3}, \mathrm{72}, \mathrm{c1}, \mathrm{a6}, \mathrm{a2}, \mathrm{46}, \mathrm{ae}, \mathrm{63}, \mathrm{f7}, \mathrm{4f}, \mathrm{93}, \mathrm{1e}, \mathrm{83}, \mathrm{65}, \mathrm{e1}, \mathrm{5a}, \mathrm{08}, \mathrm{9c}, \mathrm{68}, \mathrm{d6}, \mathrm{19}, \mathrm{00}, \mathrm{00}, \mathrm{00}, \mathrm{00}, \mathrm{00}]$. Its last five bytes are zero; the file's comment describes it as the byte-reversal of a displayed hex string, but the theorem compares against the list as written, in the order written.

**Nature of the claim.** Both sides are closed terms over decidable data, so the statement is a single ground equality that is in principle verifiable by evaluation. It asserts in one stroke that the serializer, the double-SHA-256, and the two constant tables agree on this one example, and in particular (since the `txid` sits inside the hashed data) that $\texttt{txid}(\texttt{genesisCoinbase})$ has the specific value that makes the final hash come out as `genesisHash` — though the statement does not name that intermediate value.

**What is not said.** The theorem does not state that $\texttt{txid}(\texttt{genesisCoinbase})$ equals the literal `genesisMerkleRoot` (that is the separate `genesis_merkle`). It does not state that `genesisHeader.merkleRoot` equals `genesisMerkleRoot`. It makes no claim about `genesisBlock`, about `blockWeight`, about any header other than this one, or about the SHA-256 function on any other input. It does not say the hash is below any target, nor anything about the display order of hashes. It is one ground equality between two 32-byte strings.
