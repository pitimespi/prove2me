# Read-back: `BitcoinScript.execOp_opCount`

**Binders and hypothesis.** Universally quantified: $f$, a flags record; $o$, an oracle; $e$, a Boolean (the "currently executing" argument of `execOp`, called $\mathit{fExec}$ in the definition); $c$, a byte (any value $\mathtt{0x00}$–$\mathtt{0xff}$); $s$ and $s'$, two machine states (each with a main stack, alt stack, condition stack, and natural-number `opCount`). One hypothesis, $h$:
$$\mathrm{execOp}(f, o, e, c, s) = \mathrm{some}(s'),$$
i.e. executing the single opcode $c$ from state $s$ (with executing-flag $e$) succeeds and produces $s'$.

**Conclusion.** A conjunction about the natural numbers $s.\mathrm{opCount}$ and $s'.\mathrm{opCount}$:
$$s.\mathrm{opCount} \le s'.\mathrm{opCount}\quad\wedge\quad\big(s'.\mathrm{opCount} = s.\mathrm{opCount}\ \vee\ s'.\mathrm{opCount} \le 201\big),$$
with $201 = \mathrm{MAX\_OPS\_PER\_SCRIPT}$. In words: a successful `execOp` never decreases the operation count, and either leaves it unchanged or leaves it at a value not exceeding $201$.

**Unfolding `execOp`.** `execOp` is a chain of cases on $c$. Every branch except one returns a state whose `opCount` field is copied from $s$ unchanged (branches that return $s$ itself, or $s$ with only the `stack`, `altstack` or `vfExec` fields replaced, including `pushNum`, which touches only the stack). The single exception is the CHECKMULTISIG / CHECKMULTISIGVERIFY branch ($c = \mathtt{0xae}$ or $\mathtt{0xaf}$). There, after reading the key count $n_K$ from the top element with $\mathrm{toNum}(\text{false},4,\cdot)$ and requiring $0 \le n_K \le 20$, it sets $\mathit{opCount}' := s.\mathrm{opCount} + n_K$ and **fails (none) if $201 < \mathit{opCount}'$**; if all subsequent checks succeed the returned state has $\mathrm{opCount} = \mathit{opCount}'$. The hypothesis $h$ rules out the failure, so in that branch $s'.\mathrm{opCount} = s.\mathrm{opCount} + n_K \ge s.\mathrm{opCount}$ and $s'.\mathrm{opCount} \le 201$; in all other branches $s'.\mathrm{opCount} = s.\mathrm{opCount}$. The theorem's disjunction mirrors these two situations but does not name them: it only says "unchanged, or at most $201$".

**Scope.** $e$ is unconstrained: the statement covers calls with $e = \text{false}$, which `step` makes only for conditional opcodes but which `execOp` as a function accepts for any $c$. $c$ is unconstrained: for bytes on which `execOp` always fails (OP_RETURN, unknown bytes, disabled bytes), the hypothesis is unsatisfiable and the theorem holds vacuously for those $c$. The states $s$ and $s'$ are unconstrained beyond $h$: in particular $s.\mathrm{opCount}$ may already exceed $201$ (then the first disjunct, equality, is what the non-multisig branches provide; the multisig branch cannot succeed from such an $s$ since $s.\mathrm{opCount} + n_K > 201$). Flags and oracle are arbitrary; the `nulldummy` flag and the oracle's `checkSig` influence whether the multisig branch succeeds but not the arithmetic of the count.

**Note on the second disjunct.** The conclusion's second conjunct is a disjunction, not a conjunction: it does **not** assert $s'.\mathrm{opCount} \le 201$ outright. If $s.\mathrm{opCount} = 500$ and $c = \mathrm{OP\_NOP}$, the theorem is satisfied via the equality disjunct even though $500 > 201$.

**What is not said.** The theorem does not say by how much the count can increase (no bound of $20$, no mention of $n_K$). It does not say which opcodes change the count, nor that only CHECKMULTISIG does. It does not concern `step`, which performs its own $+1$ increment and its own $201$ check *before* calling `execOp` — the theorem is about `execOp` alone, so nothing is said about the total effect of one loop iteration or about `opsIn`. It does not say anything about the stacks, `vfExec`, or stack sizes of $s'$. It does not say that `execOp` fails when the count would exceed $201$ (that is the contrapositive-shaped fact one might expect, but the statement only speaks about successful executions). It is not an "iff": no claim that a count $\le 201$ implies success.
