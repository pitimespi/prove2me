# Read-back: `BitcoinScript.op_count_fails`

**Binders and hypothesis.** Universally quantified: $f$, a flags record (three Booleans); $o$, an oracle; $\mathit{stack}$, a list of byte lists (the initial main stack, arbitrary, possibly empty, possibly longer than $1000$); $\mathit{script}$, a list of instructions. One hypothesis, $h$:
$$201 < \mathrm{opsIn}(\mathit{script}),$$
i.e. the static count $\mathrm{opsIn}(\mathit{script})$ is at least $202$ (strict inequality against $\mathrm{MAX\_OPS\_PER\_SCRIPT} = 201$).

**Unfolding `opsIn`.** $\mathrm{opsIn}([]) = 0$; a push instruction contributes $0$; an instruction $\mathrm{op}(c)$ contributes $1$ if $\mathrm{OP\_16} < c$ (i.e. $c > \mathtt{0x60}$) and $0$ otherwise. So the hypothesis says: $\mathit{script}$ contains at least $202$ opcode instructions whose byte exceeds $\mathtt{0x60}$, counting every occurrence regardless of position, regardless of whether it would sit inside a non-executed conditional branch, and regardless of what the opcode does (NOPs, disabled bytes, unknown bytes, CHECKMULTISIG all count once each; OP_1NEGATE, OP_RESERVED, OP_1–OP_16 and pushes never count).

**Conclusion.**
$$\mathrm{evalScript}(f, o, \mathit{stack}, \mathit{script}) = \text{none}.$$
Evaluating $\mathit{script}$ from the initial state $\langle \mathit{stack}, [], [], 0\rangle$ (given main stack, empty alt stack, empty condition stack, operation count $0$) fails.

**Unfolding the mechanism (as the code defines it).** `evalScript` is `run` from `State.initial`, mapped to the main stack. `run` processes instructions in order and stops with none at the first failing `step`. For an instruction $\mathrm{op}(c)$ with $c > \mathtt{0x60}$, `step` first tests $201 < \mathrm{opCount} + 1$ and returns none if so; otherwise it increments `opCount` by one and continues. This test runs for every such opcode — executed or not, disabled or not — before any other processing. Pushes and opcodes $\le \mathtt{0x60}$ never change `opCount`; the CHECKMULTISIG branch of `execOp` may additionally add $n_K \ge 0$ to it, and only ever increases it. Hence, as the code is written, along any successful prefix of the run the count is at least the number of counted opcodes processed so far; by the time the $202$nd counted opcode is reached (if the run has not already failed for another reason), the count is at least $201$ and that step fails. The theorem asserts the resulting none without naming the failing step or reason.

**Scope.** Flags and oracle are arbitrary and the conclusion is uniform in them. The initial stack is arbitrary; a stack already exceeding $1000$ elements, or a script that fails for a different reason (stack underflow, OP_RETURN, unbalanced conditional), still satisfies the conclusion since the conclusion is simply "none". The hypothesis is satisfiable (e.g. $202$ copies of $\mathrm{op}(\mathrm{OP\_NOP})$), so the theorem is not vacuous.

**What is not said.** The theorem does not say that scripts with $\mathrm{opsIn} \le 201$ succeed, nor that $202$ is the exact threshold (no converse). It does not account for the dynamic contribution of CHECKMULTISIG to the count: a script with, say, $190$ counted opcodes and a 20-key CHECKMULTISIG is not covered by the hypothesis, and nothing is asserted about it. It is stated for `evalScript` (count starting at $0$) rather than for `run` from an arbitrary state. It says nothing about `verifyScriptPlain`, where the count is reset between the two scripts, so a scriptSig and scriptPubKey whose *combined* count exceeds $201$ are not covered. It does not identify the position at which failure occurs or state that failure happens at the $202$nd counted opcode. It does not mention the stack-size limit, element-size limit, or disabled opcodes.
