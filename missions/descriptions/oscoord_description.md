## The claim

OpenSearch (and Elasticsearch since 7.0) keeps the metadata of a cluster — which indices exist, their mappings and settings, which node holds which shard — in a single *cluster state* that one elected node, the **cluster-manager** (formerly "master"), publishes to all others. The algorithm that elects the cluster-manager and makes every published state durable is a Paxos/Raft-like consensus protocol, introduced in Elasticsearch 7.0 as "Zen2". Its core is one class, `CoordinationState`, which every node runs: a state machine with a persisted part (the current term and the last accepted cluster state) and a transient part (election votes, publication votes), driven by seven handlers — `setInitialState`, `handleStartJoin`, `handleJoin`, `handleClientValue`, `handlePublishRequest`, `handlePublishResponse`, `handleCommit`. The class cites Elastic's TLA+ specification `ZenWithTerms` as its formal model; that specification is model-checked with TLC on a small instance (three nodes, terms up to 2, versions up to 3). Elastic's repository of formal models also contains an Isabelle/HOL proof of consistency for an alternative model of the algorithm. Neither is a statement about the Java code.

This mission transcribes `CoordinationState` at OpenSearch revision `b2a54ba5c0defba3d1d20423e911d4bf920bab19` and proves its per-node properties. The cluster-level safety properties are the subject of the `OpenSearchSafety` mission, which builds on this transcription (it imports this mission's definitions, not its theorems) and proves them for a cluster model in which every node runs it, assuming compatible bootstrap configurations and the default election strategy: one cluster-manager per term (`one_master_per_term`), one state per term and version (`one_state_per_version`), committed states never fork (`committed_linear`), and the assertions of `invariant()` never fail at a cluster-manager-eligible node (`javaInvariant_reachable`).

## The transcription

A node is identified by its id and carries its cluster-manager-eligible role. A **voting configuration** is a set of node ids; a set of votes is a **quorum** of it when it contains more than half of its members (`VotingConfiguration.hasQuorum`). Votes are counted only from cluster-manager-eligible nodes (`VoteCollection.addVote`). A **cluster state** is reduced to the fields `CoordinationState` reads or writes: term, version, metadata version (used instead of the version for term-0 states, `getVersionOrMetadataVersion`), last committed and last accepted configurations, the cluster-manager node (read only by the Zen1 compatibility branch), the cluster-UUID flags, and an opaque payload.

The handlers are transcribed check by check, in the Java order, each returning either a rejection or the new state with its output:

- `handleStartJoin` moves to a strictly higher term and votes (a `Join`) for the requesting node, carrying the node's last accepted term and version (the metadata version, for a term-0 state);
- `handleJoin` counts a vote for the current term, once the node has handled a start-join since its last restart and has been bootstrapped, from a voter whose accepted state is no fresher than the node's own; it recomputes `electionWon` as "the votes are a quorum of both the last committed and the last accepted configuration" (plus a pluggable election-strategy constraint);
- `handleClientValue` lets an elected node that has accepted its own last publication publish a new state of its term with a higher version, reconfiguring only when no reconfiguration is pending and only to a configuration in which its votes are a quorum;
- `handlePublishRequest` accepts a state of the current term unless it has the last accepted term and a version no higher than the last accepted one (at a node whose accepted term is at most its current term, this means a state newer than the last accepted one), and, in the compatibility branch for clusters upgrading from Zen1, even such a state when its term is 0, it names a cluster-manager, and the last accepted state names none or a different one;
- `handlePublishResponse` counts publication votes and emits an `ApplyCommitRequest` once they are a quorum of both the last committed configuration and the configuration being published;
- `handleCommit` marks the last accepted state committed (its accepted configuration becomes the committed one).

Java `assert`s are disabled in production and are caller contracts; the transcription does not check them. The asserted preconditions of `setInitialState` and `handleClientValue` are kept as separate predicates (`initialStateContract`, `clientValueContract`), which no theorem of this mission uses; the cluster model of the `OpenSearchSafety` mission imposes them at the steps that call these methods, and delivers a join only to its target. The assertion of `markLastAcceptedStateAsCommitted` about unknown cluster UUIDs and the assertions of the `Join` and `PublishResponse` constructors that their versions are non-negative are not represented. The remote cluster-state store (the REMOTE persisted state) is omitted: the handlers read it only to decide whether to write it, every value they compute comes from the LOCAL persisted state, and a failed remote write only makes the Java method throw after its local effects; the transcription returns the output instead, so the Java run is the transcription's run with that output lost, which a cluster model whose messages may be lost includes.

## What is proved

- **Quorums**: two quorums of the same configuration intersect; a superset of a quorum is a quorum; the empty configuration has no quorum; no votes are no quorum; only eligible votes count.
- **Handler specifications**: what each handler other than `setInitialState` requires and changes (`handleStartJoin_spec`, which characterizes the handler in both directions; `handleJoin_spec`; `handleClientValue_spec`; `handlePublishRequest_spec`, which assumes that the accepted term is at most the current term; `handlePublishResponse_spec`; `handleCommit_spec`); apart from `handleStartJoin_spec`, they state what a successful call implies, not when a call succeeds.
- **Monotonicity**: at a node whose last accepted term is at most its current term, every successful handler call (of `setInitialState`, with a state of term 0, as Java asserts) preserves that inequality, `handleStartJoin` strictly raises the current term, and every other handler leaves it unchanged; at such a node, a publication is accepted only if it is strictly newer than the last accepted state in the (term, version) order or has term 0 (the Zen1 compatibility branch, whose condition on the cluster-manager the statement does not record).
- **Elections**: a node only counts votes from voters whose accepted state is no fresher than its own; for a monotone election strategy (the default is), a won election stays won at a node whose `electionWon` agrees with its votes — the assertion at `CoordinationState.java:323-324`.
- **The assertions of `invariant()`**: they hold for a freshly started node whose persisted accepted term is at most its persisted current term; `handleStartJoin` re-establishes them at any node whose accepted term is at most its current term; for a monotone election strategy (the theorem assumes it for all three handlers), `handleJoin`, `handleClientValue` and `handlePublishResponse` preserve them. `handlePublishRequest` does **not** preserve them in isolation: for the default strategy, an explicit node satisfies `invariant()`, accepts a publication, and violates it. (`handleCommit` and `setInitialState`, which like `handlePublishRequest` change the configurations, are not covered by any theorem either.) That `invariant()` holds at every cluster-manager-eligible node of every execution is therefore a property of the whole cluster, which the `OpenSearchSafety` mission proves for its cluster model, assuming compatible bootstrap configurations and the default election strategy (`javaInvariant_reachable`).

## Vectors

OpenSearch's own unit tests are replayed against the transcription (`tests/OpenSearchCoordinationVectors.lean`): 40 tests of `CoordinationStateTests.java` and `testVotingConfiguration` of `CoordinationMetadataTests.java`, 179 checks, each proved by `decide`. Every Java assertion holds, with two exceptions. Four copy-equality assertions about `VoteCollection.equals` in `testVoteCollection` fail: Java compares the maps of voters (and the recorded joins, none there), the transcription's `=` also compares the order in which the votes were added (no handler compares vote collections); they hold with set equality of the voters, which is checked instead. And the two tests that expect a Java `AssertionError` (`testJoinWithWrongTarget`, `testHandleClientValueWithIllegalCommittedConfigurationChange`) are recorded with a supplementary check, since the transcription does not check `assert`s. The randomized cluster test `testSafety` and the tests of the remote cluster-state store are not replayed; the properties `testSafety` checks (one cluster-manager per term, one state per term and version, and `invariant()` at every node, all of them cluster-manager-eligible there) are proved for the cluster model of the `OpenSearchSafety` mission (`one_master_per_term`, `one_state_per_version`, `javaInvariant_reachable`), under that mission's assumptions.
