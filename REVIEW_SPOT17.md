## Verdict

No defect. SHA-256: big-endian message words, the 64 round constants (extracted from
`Transform` and compared to `sha256K` as a list: equal), the schedule
`w[t] = σ1(w[t-2]) + w[t-7] + σ0(w[t-15]) + w[t-16]`, the round `t1 = h + Σ1(e) + Ch(e,f,g) + k + w`,
`t2 = Σ0(a) + Maj(a,b,c)`, `(a,…,h) ← (t1+t2, a, b, c, d+t1, e, f, g)`, the eight initial words,
MD padding `0x80`, zeros to 56 mod 64, 64-bit **big-endian** bit length, and big-endian output
words all agree with Core. RIPEMD-160: little-endian message words, the five functions, the left
constants `0, 5A827999, 6ED9EBA1, 8F1BBCDC, A953FD4E` with `f1..f5` and the right constants
`50A28BE6, 5C4DD124, 6D703EF3, 7A6D76E9, 0` with `f5..f1`, the four 80-entry tables (word indices
and rotation amounts of both lines, extracted from the `R..` calls of `Transform` and compared
with `ripemdRL/RR/SL/SR`: all four equal), the step `a ← rol(a + f + x + k, r) + e; c ← rol(c,10)`
with the register rotation, the final combination `(b+c₁+d₂, c+d₁+e₂, d+e₁+a₂, e+a₁+b₂, a+b₁+c₂)`,
the five initial words, **little-endian** bit length and little-endian output. `hash256` and
`hash160` compose them as `hash.h`. The blind read-back describes exactly these choices (it notes
`sha1` reuses `ripemdInit`, whose five values are the SHA-1 IV, and the vectors confirm `sha1`).

Vectors: `tests/HashVectors.lean` (86 `#eval` lines, all `true`), generated by
`tests/reference/hash_reference.py` from Python `hashlib` (its SHA-256, SHA-1 and RIPEMD-160 are
first asserted against the published vectors: `""`, `"a"`, `"abc"`, `"message digest"`, the

about 75 s for SHA-256 and RIPEMD-160 together, so no fallback to a smaller message was needed; a

## `CSHA256::Write/Finalize`, `sha256::Transform` — `sha256`

Core: `Write` buffers into 64-byte blocks and calls `Transform` per block; `Finalize` writes
`1 + ((119 - bytes % 64) % 64)` bytes of `{0x80, 0, …}` then `WriteBE64(bytes << 3)`, and emits
`s[0..8]` with `WriteBE32`. `Transform` reads `w0..w15` with `ReadBE32`, runs 64 `Round`s whose
argument order rotates the registers, with the schedule words updated in place
(`w0 += sigma1(w14) + w9 + sigma0(w1)`, i.e. indices `t-2, t-7, t-15, t-16` modulo 16), then adds
the working variables into `s`.

The Lean: `mdPad true` appends `0x80`, `(119 - len % 64) % 64` zeros and `beBytes 8 (len * 8)`;
`chunks64` splits (the padded length is always a multiple of 64, so nothing is dropped);
`sha256Compress` = `be32Words`, `sha256Schedule` (48 appended words with `getD`, every index in
range), `zipWith (+) sha256K`, 64 `sha256Round`s, word-wise addition; output `be32Bytes` of the
eight words. `rotr x n = (x >>> n) ||| (x <<< (32 - n))` for `n ∈ {2,13,22,6,11,25,7,18,17,19}` is
Core's `(x >> n | x << (32-n))`. Identical; Core's SSE4/AVX2/SHA-NI `Transform` variants are
performance paths of the same function (not in the cached source, not needed).

## `CRIPEMD160::Write/Finalize`, `ripemd160::Transform` — `ripemd160`

Core: same buffering; `Finalize` uses `WriteLE64(bytes << 3)` and `WriteLE32` output. `Transform`
reads `w0..w15` with `ReadLE32`, runs the left (`R11..R51`) and right (`R12..R52`) lines
interleaved but independent, each 80 `Round`s with the register rotation
`(a,b,c,d,e) → (e, a', b, c', d)` expressed by the argument order, and combines
`s[0] = s[1]+c1+d2; s[1] = s[2]+d1+e2; s[2] = s[3]+e1+a2; s[3] = s[4]+a1+b2; s[4] = t+b1+c2`.
Since the argument order has period 5 and 80 ≡ 0 (mod 5), after the last round the variable
named `a1` is again in the `a` role (checked by extracting the role sequence from the source), so
the names in the combination are the role-ordered final state.

The Lean: `mdPad false` (little-endian length), `le32Words`, `ripemdLine` folding `ripemdStep`
over `j < 80` with `fsel j b c d`, `w[rsel[j]]`, `ksel j`, `ssel[j]`; `ripemdStep` returns
`⟨e, rol(a+f+x+k, r) + e, b, rol c 10, d⟩`; `ripemdCompress` combines
`⟨b + l.c + r.d, c + l.d + r.e, d + l.e + r.a, e + l.a + r.b, a + l.b + r.c⟩` where `l`/`r` are the
role-ordered final states, which is Core's combination. Output `le32Bytes`. Identical.

## `CSHA1` — `sha1`

Not in the spot's list but defined in the file and cheap to check: `f`/`K` by 20-round groups,
schedule `rol(w[t-3] ^ w[t-8] ^ w[t-14] ^ w[t-16], 1)`, round
`temp = rol(a,5) + f + e + K + w[t]`, `(a,b,c,d,e) ← (temp, a, rol(b,30), c, d)`, big-endian
length and output, IV `67452301 EFCDAB89 98BADCFE 10325476 C3D2E1F0` (shared with RIPEMD-160 via
`ripemdInit`). The vectors (`"abc"`, the 56-byte message, the padding-boundary messages, 1000 ×
`'a'`) all pass. Not used by any consensus definition.

## `Hash`, `Hash160` — `hash256`, `hash160`

Core: `Hash(x) = SHA256(SHA256(x))`; `CHash160` = `RIPEMD160(SHA256(x))`. The Lean: `hash256 m =
sha256 (sha256 m)`, `hash160 m = ripemd160 (sha256 m)`. Vector: `hash160` of the genesis output
public key is `62e907b15cbf27d5425399ebf6f0fb50ebb88f18` (the P2PKH hash of
`1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa`).

## Checks from the guide

- **Order of tests.** No tests; the order of operations (padding, word order, round order,
  combination) is Core's.
- **Constants.** SHA-256 IV (8 words), 64 round constants, RIPEMD-160 IV, 10 additive constants,
  4 × 80 table entries, rotation amounts (2/13/22, 6/11/25, 7/18/3, 17/19/10; RIPEMD `rol 10`),
  SHA-1 constants: all match (constants and tables also compared programmatically against the
  C++).
- **Integer semantics.** All arithmetic is `UInt32` with wrap-around, as `uint32_t`; shift
  amounts never equal 0 or 32, so Lean's modulo-32 shift semantics do not matter; the bit length
  is `len * 8` as `Nat` reduced to 8 bytes (`bytes << 3` as `uint64_t`), equal for every input
  below 2^61 bytes.
- **Defaults.** `getD … 0` in the schedules and table lookups is never reached: the schedules
  start from 16 words and only read back ≤ 16 positions; the tables have 80 entries for
  `j < 80`; `chunks64`/`be32Words`/`le32Words` drop nothing on a padded message.
- **Policy vs consensus.** Pure functions; no policy content.
