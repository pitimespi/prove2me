## Verdict

No defect. The five buried heights, the two exception hashes and their flag sets, the
replace-then-OR structure of `GetBlockScriptFlags`, the `≥` of `DeploymentActiveAt` and the
`+ 1 ≥` of `DeploymentActiveAfter`, and the `nLockTimeFlags` selection all agree with Core. On
Taproot: at this revision Core has **no** `DEPLOYMENT_TAPROOT` at all (`DeploymentPos` holds only
`DEPLOYMENT_TESTDUMMY`, `CMainParams` sets no Taproot `BIP9Deployment`, and `validation.cpp` never
calls `DeploymentActiveAt` with a versionbits deployment); `SCRIPT_VERIFY_TAPROOT` sits in the
unconditional base `P2SH | WITNESS | TAPROOT` of `GetBlockScriptFlags`, and only the
`script_flag_exceptions` entry for block `0000…95ad` removes it. The Lean's `baseFlags` with
`taproot := true` and `exceptionBase .taprootBlock` with `taproot := false` is therefore not a
simplification of Core but exactly Core's rule, for every height including 0..481823 and
481824..709631. Whether that rule reproduces the historical BIP9 activation at 709632 is Core's
own claim (the comment at `validation.cpp:2255`: "only one historical block violated the TAPROOT
rules"), which the cached source cannot verify and which this review does not assess; it is not
among the limits L1–L10 because the model does not deviate from Core here. The blind read-back
(`scratchpad/audit8/readback_Def_BitcoinActivation.md`) describes every declaration as Core
reads, including that `heightInCB` is unused by `blockScriptFlags` (correct: BIP34 enters
`ContextualCheckBlock` through `activeAfter`, spot 13) and that the exception label only changes
the first three fields.

Vectors: `tests/ActivationVectors.lean` (114 lines, all `true`), generated by
`tests/reference/activation_reference.py`, an independent Python transcription of the C++ with
the flags as named bits mapped to the Lean's seven-field record.

## `CMainParams` — `deploymentHeight`, `exceptionBase`, `BitcoinBlockV2.scriptException`

Core (`chainparams.cpp:115–125`): `script_flag_exceptions` has two entries,
`00000000000002dc756eebf4f49723ed8d30cc28a5f108eb94b1ba88ac4f9c22 ↦ SCRIPT_VERIFY_NONE` (the BIP16
exception) and `0000000000000000000f14c35b2d841e986ab5441de8c585d5ffe55ea1e395ad ↦ SCRIPT_VERIFY_P2SH |
SCRIPT_VERIFY_WITNESS` (the Taproot exception); `BIP34Height = 227931`, `BIP34Hash = 0000…08b8`,
`BIP65Height = 388381`, `BIP66Height = 363725`, `CSVHeight = 419328`, `SegwitHeight = 481824`,
`MinBIP9WarningHeight = 711648`. `DeploymentHeight` (`params.h:143`) maps `HEIGHTINCB → BIP34Height`,
`CLTV → BIP65Height`, `DERSIG → BIP66Height`, `CSV → CSVHeight`, `SEGWIT → SegwitHeight`.

The Lean: `deploymentHeight` gives `heightInCB ↦ 227931`, `cltv ↦ 388381`, `derSig ↦ 363725`,
`csv ↦ 419328`, `segwit ↦ 481824` (the CLTV/DERSIG pairing is the one place a transcription could
swap values; it is right: BIP66/DERSIG is the lower height 363725). `exceptionBase` gives
`.none ↦ baseFlags = ⟨T,T,T,F,F,F,F⟩`, `.bip16Block ↦ noFlags`, `.taprootBlock ↦ ⟨T,T,F,F,F,F,F⟩`,
i.e. `NONE` and `P2SH | WITNESS`. The lookup by hash is `BitcoinBlockV2.scriptException`
(`Def_BitcoinBlockV2.lean:65`): equality of the serialized (little-endian) hash with
`bip16ExceptionHash` / `taprootExceptionHash`, whose byte lists are the display hex reversed
(checked byte by byte in the reference: `22 9c 4f ac …` and `ad 95 e3 a1 …`). `BIP34Hash` is
consumed by the BIP30 skip in `ConnectBlock` (`bip34Hash`, spot 10), not here.
`MinBIP9WarningHeight` is not referenced anywhere in the cached `validation.cpp`; it belongs to
the version-bits warning logic and is not consensus, so its absence from the model is correct.

## `DeploymentActiveAt` / `DeploymentActiveAfter` — `activeAt` / `activeAfter`

Core (`deploymentstatus.h`): for a `BuriedDeployment`, `DeploymentActiveAt(index, dep) =
index.nHeight >= DeploymentHeight(dep)` and `DeploymentActiveAfter(pindexPrev, dep) =
(pindexPrev == nullptr ? 0 : pindexPrev->nHeight + 1) >= DeploymentHeight(dep)`. The
`DeploymentPos` overloads go through `VersionBitsCache`; nothing in the consensus path uses them at
this revision (the only `DeploymentPos` is `DEPLOYMENT_TESTDUMMY`, never active on mainnet).

The Lean: `activeAt height dep = decide (deploymentHeight dep ≤ height)` and
`activeAfter prevHeight dep = decide (deploymentHeight dep ≤ prevHeight + 1)`. Identical for every
non-null `pindexPrev`. The null case (`pindexPrev == nullptr`, i.e. validating the genesis block)
is unreachable in the model: `initialState` already holds the genesis header, so every block the
model validates has a tip as its parent, and `connectBlock` short-circuits the genesis hash before
reading any flag. Heights are `Nat` against Core's `int`; the chain never produces a negative
height, and `prevHeight + 1` cannot wrap.

## `GetBlockScriptFlags` — `blockScriptFlags`

Core, in order: `flags = P2SH | WITNESS | TAPROOT`; if the block's hash is in
`script_flag_exceptions`, `flags = it->second` (assignment, the base is discarded, not AND-ed);
then `|= DERSIG` if `DeploymentActiveAt(DERSIG)`, `|= CHECKLOCKTIMEVERIFY` if `CLTV`,
`|= CHECKSEQUENCEVERIFY` if `CSV`, `|= NULLDUMMY` if `SEGWIT`. `block_index` is the block being
validated (`ConnectBlock` passes `*pindex`), so the tests are on the block's own height. `P2SH` is
unconditionally in the base (no `BIP16Height` exists at this revision); the one pre-BIP16 block
that spends a P2SH-shaped output is handled by the `SCRIPT_VERIFY_NONE` exception.

The Lean: `let f := exceptionBase exc` then `{ f with dersig := f.dersig || activeAt height .derSig,
cltv := … .cltv, csv := … .csv, nulldummy := … .segwit }`, with `p2sh`, `witness`, `taproot` carried
from `f`. `connectBlock` calls it as `blockScriptFlags height (scriptException hash)` with
`height := S.nextHeight`, the block's own height. The `||` with `f.*` is Core's `|=` on a base
whose four height-driven bits are always clear, so the four fields are exactly the four
`activeAt` tests whatever the exception, and on the Taproot exception block (height 692261 on
mainnet, outside the cached source) DERSIG/CLTV/CSV/NULLDUMMY are added on top of `P2SH |
WITNESS` just as Core adds them after the assignment. The record has exactly the seven flags
`GetBlockScriptFlags` can set; no other `SCRIPT_VERIFY_*` bit reaches consensus. Identical.

## `nLockTimeFlags` — `lockTimeFlags`

Core (`ConnectBlock`, `validation.cpp:2478`): `nLockTimeFlags = 0; if
(DeploymentActiveAt(*pindex, CSV)) nLockTimeFlags |= LOCKTIME_VERIFY_SEQUENCE`, and
`consensus.h:28` has `LOCKTIME_VERIFY_SEQUENCE = (1 << 0)` as the only lock-time flag at this
revision. The MTP cutoff for `IsFinalTx` is not a flag any more: `ContextualCheckBlock`
(`validation.cpp:4148`) computes `nLockTimeCutoff` from a bool `enforce_locktime_median_time_past =
DeploymentActiveAfter(pindexPrev, CSV)` (spot 13; the Lean's `contextualCheckBlock` uses
`activeAfter S.tipHeight .csv` for it).

The Lean: `lockTimeFlags height = if activeAt height .csv then LOCKTIME_VERIFY_SEQUENCE else 0`
with `LOCKTIME_VERIFY_SEQUENCE = 1`, called with the block's own height, and consumed by
`sequenceLocksOk` as `BitVec.ofNat 32 lockTimeFlags`, where `coreEnabled` tests bit 0 (spot 20).
Identical.

## Checks from the guide

- **Order of tests.** Core assigns the exception and then ORs four flags; the Lean copies the
  exception record and ORs the same four. OR is order-independent, and no test short-circuits
  another.
- **Constants.** 227931, 388381, 363725, 419328, 481824; the two exception hashes (byte order
  verified); `NONE` and `P2SH | WITNESS` for the exceptions; `P2SH | WITNESS | TAPROOT` for the
  base; `LOCKTIME_VERIFY_SEQUENCE = 1`. All match. `MinBIP9WarningHeight` and `BIP34Hash` are
  correctly outside this file.
- **Integer semantics.** Core `int` heights against `Nat`; only `≥` and `+ 1` on non-negative
  values, no subtraction, no wrap.
- **Defaults on degenerate input.** None: every function is a total table or a comparison. The
  one Core special case, a null `pindexPrev` in `DeploymentActiveAfter`, cannot arise in the model
  (the genesis is pre-loaded and `connectBlock` short-circuits it).
- **Policy vs consensus.** `STANDARD_SCRIPT_VERIFY_FLAGS` (`policy/policy.h:104`, which adds
  `TAPROOT` policy discouragements, `LOW_S`, `STRICTENC`, …) is not modeled; the versionbits
  machinery, `DEPLOYMENT_TESTDUMMY` and the BIP9 warning height are not consensus at this
  revision; testnet/signet/regtest heights and exceptions are out of scope (L8).
