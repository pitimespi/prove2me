## Verdict

No defect. Every test, its order, and every constant agree with Core. The read-back
(`missions/readbacks/blockv2/readback_Def_BitcoinBlockV2.md`, sections `CheckBlock` and
`ContextualCheckBlock`) describes the Lean exactly as Core reads, which is the blind check that
the transcription says what it is meant to say.

Vectors: `tests/CheckBlockVectors.lean` (47 lines, all `true`), generated by
`tests/reference/checkblock_reference.py`, an independent Python transcription of the C++.
It uses mainnet block 586 (hash `000000000d0d23516c5efd3af4eb951603bb30b2c93884b522a318b30e918ee7`,
three transactions, so its merkle tree has an odd level) for the full `checkBlock` with real proof

## `CheckBlock` — `checkBlock`

Core, in order: `fChecked` cache (no effect on the verdict); `CheckBlockHeader` =
`CheckProofOfWork(block.GetHash(), block.nBits)` (`fCheckPOW` is true on the validation path,
`ConnectBlock` passes `!fJustCheck`); signet solution (not mainnet); `CheckMerkleRoot`
(`fCheckMerkleRoot` true on the same path); size limits: `vtx` non-empty, `vtx.size() * 4 ≤
4,000,000`, `GetSerializeSize(TX_NO_WITNESS(block)) * 4 ≤ 4,000,000`; first transaction a coinbase,
no other; `CheckTransaction` on every transaction; `GetLegacySigOpCount` summed over every
transaction, `* 4 ≤ 80,000`.

The Lean is the same conjunction in the same order: `checkHeaderPow` (`hashValue` of the header
against `deriveTarget nBits`, the PoW mission's `checkProofOfWork`, which rejects a zero,
negative, overflowing or above-`powLimit` target as Core does); `blockMerkleRoot` equal to
`header.merkleRoot` and the mutation flag clear; `!vtx.isEmpty`; `vtx.length * 4 ≤ 4,000,000`;
`(serBlock false b).length * 4 ≤ 4,000,000`; `isCoinBase (vtx.headD genesisCoinbase)` (the default
is only read when `vtx` is empty, already rejected); `(vtx.drop 1).all (!isCoinBase)`;
`vtx.all checkTransaction`; `(vtx.map legacySigOpCount).sum * 4 ≤ 80,000`. Constants
`WITNESS_SCALE_FACTOR = 4`, `MAX_BLOCK_WEIGHT = 4,000,000`, `MAX_BLOCK_SIGOPS_COST = 80,000` match
`consensus.h`. The Lean `&&` evaluates the same tests Core does; a `Bool` conjunction has no
state, so the order only matters for which reason Core reports, not for the verdict.

Dependencies checked elsewhere: `serBlock false` is `TX_NO_WITNESS` block serialization
(serialization is area 1, outside this review's spots: the length is header 80 + CompactSize +
stripped transactions, and the vector `(serBlock false mutated586).length == 80 + 1 + Σ` confirms
it on real data); `checkTransaction` is spot 21; `legacySigOpCount` is spot 11.

## `CheckMerkleRoot` — `blockMerkleRoot`

Core: `BlockMerkleRoot(block, &mutated)` with leaves `vtx[i]->GetHash()` (the txid, witness
stripped); root mismatch → `bad-txnmrklroot`; `mutated` → `bad-txns-duplicate`. `ComputeMerkleRoot`
with a non-null `mutated` tests, at every level before the odd-duplication, every pair at an
*even* position for equality; an odd level duplicates its last hash; the root of no hashes is
`uint256()`.

The Lean: `BitcoinMerkle.computeMerkleRoot merkleCombine zeroHash (vtx.map txid)`, the Merkle
mission's transcription of the same loop (its mutation theorems were proved there), with
`merkleCombine a b = hash256 (a ++ b)` = `SHA256D64` on the concatenated pair and `zeroHash` for
the empty case. Both components are compared in `checkBlock`. Identical.

Vectors: block 586 gives `(root, false)` with the header's root; `[a, b, c, c]` gives the same root
with the flag set, and `checkBlock` rejects it while every other test passes (the CVE-2012-2459
case: the only thing that rejects the block is the flag); `[a, b, c, b, c]` and `[a, b, b]` have
different roots and no flag (the equal pair of `[a, b, b]` sits at an odd position, which Core
does not test, and the Lean agrees); an empty `vtx` gives `(zeroHash, false)` and is rejected.

## `GetWitnessCommitmentIndex` — `witnessCommitmentIndex`

Core: `-1` for an empty block; otherwise the *last* coinbase output whose `scriptPubKey` has at
least `MINIMUM_WITNESS_COMMITMENT = 38` bytes and starts with `6a 24 aa 21 a9 ed`
(`OP_RETURN`, push of 36, the four magic bytes). Only `vtx[0]` is scanned.

The Lean: `none` for `[]`; else `getLast?` of the indices `i < cb.vout.length` with
`isCommitmentOutput (cb.vout.getD i ⟨0, []⟩)`, where `isCommitmentOutput` is `38 ≤ length` and
`take 6 = [6a, 24, aa, 21, a9, ed]`. The `getD` default is never read because `i` ranges over valid
indices. Identical.

Vectors: last of two commitments wins; trailing bytes after 38 are ignored; a 37-byte output or a
wrong sixth byte is not a commitment; a commitment-shaped output in a non-coinbase transaction is
not found; empty block and empty coinbase give `none`.

## `CheckWitnessMalleation` — `checkWitnessMalleation`

Core, with `expect_witness_commitment` (= SegWit active for the block being validated, see spot 13):
if expected and a commitment exists at `commitpos`: the coinbase's first input's witness stack
must have exactly one element of exactly 32 bytes (`bad-witness-nonce-size`); then
`hash_witness = BlockWitnessMerkleRoot(block)` (leaf 0 is the zero hash, the others
`GetWitnessHash()`, which is the txid for a transaction without witness, no mutation check);
`CHash256(hash_witness ‖ nonce)` must equal `scriptPubKey[6..38)` of the commitment output
(`bad-witness-merkle-match`); accept. In every other case (not expected, or expected with no
commitment) no transaction may have a witness (`unexpected-witness`). `HasWitness` is "some input
has a non-empty witness stack".

The Lean: `noWitness := vtx.all (fun tx => !tx.hasWitness)` with `Tx.hasWitness = vin.any
(!witness.isEmpty)`; `expect = false → noWitness`; `expect = true`: `witnessCommitmentIndex = none
→ noWitness`; `some pos →` the first input's witness of the first transaction must match `[nonce]`
(any other shape, including the empty stack, is `false`), `nonce.length = 32`, and
`hash256 (blockWitnessMerkleRoot b ++ nonce) = (spk.drop 6).take 32` for the commitment output,
where `blockWitnessMerkleRoot = (computeMerkleRoot … (zeroHash :: (vtx.drop 1).map wtxid)).1` and
`wtxid tx = if tx.hasWitness then hash256 (serTx true tx) else txid tx`. Identical. The `headD`
defaults for the coinbase and its first input are never reached on the validation path: a
commitment index implies a non-empty `vtx`, and `checkBlock` has already required the first
transaction to be a coinbase, hence to have exactly one input, which is Core's `assert`.

Vectors (19 malleation cases): correct commitment in either output position; two commitments
with the last one deciding; trailing bytes; 37-byte and wrong-prefix outputs with a witness
present (rejected as unexpected witness); no commitment with and without witnesses; 31-byte
nonce; two-element and empty stacks; commitment over a different transaction order; a block with
one transaction and with only the coinbase (root = the zero leaf); and the four
`expect = false` cases, where a valid commitment does not excuse witness data.

## Checks from the guide

- **Order of tests.** Same as Core; verdict-only semantics make the remaining differences moot.
- **Constants.** 38, 4, 4,000,000, 80,000, the six magic bytes, the 32-byte nonce, the 6..38 slice:
  all match.
- **Integer semantics.** Sizes and counts are `Nat` with `≤` against the limits, as Core's
  unsigned comparisons; no subtraction is involved.
- **Defaults.** `headD`/`getD` defaults are all behind tests that make them unreachable on the
  validation path (noted above).
- **Policy vs consensus.** `CheckBlock` has no policy content; the `fChecked` and
  `m_checked_*` caches are performance only.
