## Verdict

No defect. Every constant (`1 << 31`, `1 << 22`, `0xffff`, shift 9, `LOCKTIME_VERIFY_SEQUENCE =
1`), the unsigned `version >= 2` test, the `−1` initial values, the `prevHeights[i] = 0` for
disabled inputs, the two `− 1` offsets, the ancestor at `max(nCoinHeight − 1, 0)`, the strict
`<` of `EvaluateSequenceLocks` against the block's own height and the *previous* block's MTP, all
agree. The bridge `BitcoinBlockV2.sequenceLocksOk` builds the context from the block's own height
and the chain's MTP-by-height function, so `mtp (height − 1)` is `pprev->GetMedianTimePast()`,
and reads the coin heights from the ledger, where coins created earlier in the same block carry
the block's height exactly as `UpdateCoins(…, pindex->nHeight)` stores them in Core; the
`MEMPOOL_HEIGHT → tip + 1` substitution lives in `CalculatePrevHeights` / `CheckSequenceLocks`
(mempool policy, `validation.cpp:189`, `:217`) and is correctly absent. The only
representational difference is the known limit L9 (`mtpNat` takes `toNat` of the integer MTP).

## `CalculateSequenceLocks` — `coreEnabled`, `coreStep`, `calculate`, `returnedHeights`

Core: `nMinHeight = -1` (`int`), `nMinTime = -1` (`int64_t`); `fEnforceBIP68 = tx.version >= 2 &&
flags & LOCKTIME_VERIFY_SEQUENCE` where `tx.version` is `uint32_t` (`transaction.h:299`) so the
comparison is unsigned and `&&` binds looser than `&`; if not enforced, return `(-1, -1)` with
`prevHeights` untouched. Otherwise for each input in order: if `nSequence & (1 << 31)`, set
`prevHeights[i] = 0` and skip; else `nCoinHeight = prevHeights[i]`; if `nSequence & (1 << 22)`,
`nCoinTime = block.GetAncestor(max(nCoinHeight − 1, 0))->GetMedianTimePast()` and
`nMinTime = max(nMinTime, nCoinTime + (int64_t)((nSequence & 0xffff) << 9) − 1)`; else
`nMinHeight = max(nMinHeight, nCoinHeight + (int)(nSequence & 0xffff) − 1)`. Bits 16..21 and
23..30 play no role. `block` is the block being validated (`*pindex`), so `GetAncestor(h)` for
`0 ≤ h ≤ nHeight` is the chain's block at height `h`.

The Lean: `coreEnabled version flags = decide (2 ≤ version.toNat) && ((flags &&& 1) != 0)` on
`BitVec 32` (unsigned, bit 0). `calculate` returns `initial = ⟨-1, -1, []⟩` folded with
`coreStep` when enabled, else `⟨-1, -1, reverse coinHeights⟩`, so `returnedHeights` is the
untouched height list. `coreStep`: `coreDisabled` (`&&& 0x80000000 != 0`) → prepend `0`, minima
unchanged; else `coreTimeBased` (`&&& 0x00400000 != 0`) → `minTime := max minTime (mtp (coinHeight
− 1) + coreSeconds − 1)` in `Int`, where `coinHeight − 1` is `Nat` subtraction, i.e. exactly
`max(nCoinHeight − 1, 0)`, and `coreSeconds = ((seq &&& 0xffff) <<< 9).toNat` (at most
`0x1fffe00 < 2^32`, so the 32-bit shift loses nothing, as Core's `uint32_t` shift does not);
else `minHeight := max minHeight (coinHeight + coreDelay − 1)` with `coreDelay = (seq &&&
0xffff).toNat`. The fold is left-to-right over the inputs, as Core's loop; `max` makes the
order immaterial for the minima, and the prepend-then-reverse keeps the heights in input order.
Identical. Core's `int` / `int64_t` arithmetic is unbounded `Int` in the Lean: `nCoinHeight +
65535` overflows `int` only for `nCoinHeight > 2^31 − 65536`, unreachable on any chain (and
carried as `admissible`/`noOverflow` in the theorem); `nCoinTime + 0x1fffe00` is far inside
`int64_t`.

## `EvaluateSequenceLocks`, `SequenceLocks` — `evaluate`, `sequenceLocks`

Core: `assert(block.pprev)`; `nBlockTime = block.pprev->GetMedianTimePast()`; return `false` if
`lockPair.first >= block.nHeight || lockPair.second >= nBlockTime`, else `true`; `SequenceLocks`
composes the two.

The Lean: `evaluate ctx acc = decide (acc.minHeight < ctx.height ∧ acc.minTime < ctx.mtp
(ctx.height − 1))` in `Int`, the contrapositive of Core's two `>=`; `sequenceLocks` composes.
`ctx.height` is the block being validated and `ctx.mtp (ctx.height − 1)` the previous block's
MTP (see the bridge). The `−1` thresholds therefore give BIP68's "first valid height/time"
semantics: a height lock of `n` on a coin at `c` passes exactly when `c + n ≤ height`, a time lock
of `n` units passes exactly when `mtp(max(c − 1, 0)) + 512n ≤ mtp(height − 1)`, which is also what
`Def_BIP68_Model.inputSatisfied` states and `core_correct` proves. Identical. `ctx.height − 1`
truncates at `0`; Core asserts `pprev`, and the model never validates at height 0 (the genesis
is pre-loaded, `connectBlock` short-circuits it), so `ctx.height ≥ 1` on the validation path.

## The bridge: `ConnectBlock` → `sequenceLocksOk`

Core (`validation.cpp:2548`): for each non-coinbase transaction, after `CheckTxInputs` and the
fee range, `prevheights[j] = view.AccessCoin(tx.vin[j].prevout).nHeight` from the view *as updated
by the earlier transactions of this block* (`UpdateCoins(tx, view, …, pindex->nHeight)` runs at the
end of each iteration and `AddCoins` stores `Coin(out, nHeight, fCoinbase)`), then `SequenceLocks(tx,
nLockTimeFlags, prevheights, *pindex)`. So a coin created earlier in the same block has
`nCoinHeight = pindex->nHeight`; its time-lock ancestor is `max(nHeight − 1, 0) = pprev`, and its
height lock `nHeight + n − 1 ≥ nHeight` fails for every `n ≥ 1`.

The Lean (`Def_BitcoinBlockV2.lean:286`): `sequenceLocksOk u height mtp lockTimeFlags tx =
BitcoinBIP68.sequenceLocks (ofNat 32 tx.version) (ofNat 32 lockTimeFlags) ⟨height, mtp⟩ (tx.vin.map
fun i => ⟨ofNat 32 i.nSequence, (accessCoin u i.prevout).height⟩)`, called from `connectLoop` with
`height = S.nextHeight` (the block's height), `mtp = S.mtpNat` and `u = st.utxo`, the ledger after
`updateCoins st.utxo tx height` of the earlier transactions, which stores `⟨o, height, cb⟩`. So an
intra-block coin has `coinHeight = height`, as in Core. `S.mtpNat h = (S.mtpAt h).toNat` with
`mtpAt h = medianTimePast (timesTo h)` over the headers `0..h` (most recent first), i.e. the
MTP of the block at height `h`: `mtp (height − 1)` is the tip's MTP = `pprev->GetMedianTimePast()`,
and `mtp (coinHeight − 1)` is `GetAncestor(max(coinHeight − 1, 0))->GetMedianTimePast()`. Every
argument passed to `mtp` is `≤ height − 1 = tipHeight` (coin heights are at most the block's
height), so `timesTo`'s `take` never truncates silently. The reduction of `tx.version` and
`nSequence` to 32 bits is L2; the `toNat` is L9. A missing coin reads as the dummy with height 0
(L6) but is unreachable here because `connectLoop` runs `checkTxInputs` first (spot 10).
`CheckSequenceLocks` (mempool: `MEMPOOL_HEIGHT → tip + 1`, evaluation against a synthetic next
block) is policy and is not modeled.

## Vectors

`tests/Bip68Vectors.lean`, with an MTP table `1,000,000 + 600h` and block height 20: the four
constants and predicates (`coreDisabled`, `coreTimeBased`, `coreDelay`, `coreSeconds`, ten
`coreEnabled` cases including version `0xffffffff` and `0x80000000` enforced and flags `2` not);
then for each of 35 transactions the full `calculate` accumulator, the `returnedHeights`, and
`sequenceLocks`: empty inputs; disabled flag (minima untouched, height reported as 0, even with
the type flag and delay `0xffff`); version 1 and flags 0 / flags 2 (heights returned unchanged
though the disable flag is set); height locks with mask 0, 1, `0xffff` and coins at 0, 3, 10, 19,
20; the exact height boundary (`10 + 10 − 1 = 19` passes, `10 + 11 − 1 = 20` fails); time locks
with 0, 1, 2, 22, 23 and `0xffff` units from coins at heights 0, 1, 2 (0 and 1 both read `mtp 0`,
2 reads `mtp 1`); the time boundary (22 units from `mtp 0` is `11263 < 11400 = mtp 19 − mtp 0`,
passes; 23 units fails); five mixed inputs where the max of each kind wins and a disabled input
is ignored; the bit layout with bits 16..21 and 23..30 set, with bit 22 clear (height lock 7) and
set (time lock 7), `0xffffffff` (disabled) and `0x7fffffff` (time lock `0xffff`); intra-block
spends (coin at the block's own height: mask 1 fails, mask 0 passes, time lock 0 passes, 1 unit
fails); block height 1 with `pprev` the genesis. Then `evaluate` directly at the exact boundaries
`first = height` (fail), `height − 1` (pass), `second = mtp (height − 1)` (fail), one below
(pass), both at once, `(-1, -1)`, `(0, 0)`, and at block height 1 against `mtp 0`. An exact
`second == nBlockTime` through `sequenceLocks` is not constructible with a 600-second table
(`600k + 1` is never a multiple of 512), so that boundary is pinned on `evaluate` directly and
the `sequenceLocks` time cases bracket it from both sides. All 136 lines print `true` on the
first run; nothing in the reference or the Lean had to be corrected.

## Checks from the guide

- **Order of tests.** Disabled bit before the type bit per input, as Core; inputs folded in
  order; `max` and the `∧` of `evaluate` make the order verdict-neutral.
- **Constants.** `0x80000000`, `0x00400000`, `0x0000ffff`, shift `9`, `−1` initial values,
  `LOCKTIME_VERIFY_SEQUENCE = 1` tested as bit 0, `version ≥ 2`. All match.
- **Integer semantics.** Unsigned `version` (`uint32_t`) as `BitVec 32`; `nSequence` masks on
  `BitVec 32`; the 32-bit shift cannot truncate; minima in `Int` where Core uses `int`/`int64_t`
  (overflow unreachable, bounded in the theorem); `coinHeight − 1` and `height − 1` are `Nat`
  truncations that coincide with Core's `max(…, 0)` and with the `assert(pprev)` path.
- **Defaults on degenerate input.** `ctx.mtp` is a total function supplied by the bridge
  (`mtpAt` over `take`), never called beyond the tip on the validation path; the dummy coin
  height 0 (L6) sits behind `checkTxInputs`; the not-enforced branch returns `(−1, −1)` and the
  heights unchanged, as Core.
- **Policy vs consensus.** Only `SequenceLocks` as called from `ConnectBlock` is modeled;
  `CheckSequenceLocks` / `CalculatePrevHeights` (mempool, `MEMPOOL_HEIGHT`, `LockPoints`) are not,
  correctly.
