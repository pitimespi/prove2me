## Verdict

No defect. The four tests, their order, the cutoff rule, the height push and every constant agree
with Core. The read-back (`missions/readbacks/blockv2/readback_Def_BitcoinBlockV2.md`,
`ContextualCheckBlock` section) describes the Lean as Core reads.

Vectors: `tests/ContextualVectors.lean` (57 lines, all `true`), generated by
`tests/reference/contextual_reference.py`, an independent transcription of `IsFinalTx` and
`push_int64`/`CScriptNum::serialize`/the push-size rule. The first run of the generator produced
five wrong expectations (my synthetic chain used block times below the 500,000,000 threshold, so
the intended time locks were height locks, and a CompactSize of 3 bytes where 5 apply); the Lean
was right on all five, the reference was corrected, and the fact is recorded here because it is

## `ContextualCheckBlock` — `contextualCheckBlock`

Core: `nHeight = pindexPrev->nHeight + 1`; `enforce_locktime_median_time_past` iff
`DeploymentActiveAfter(pindexPrev, CSV)`, i.e. `nHeight ≥ 419328`; `nLockTimeCutoff` = the previous
block's `GetMedianTimePast()` if so, else `block.GetBlockTime()`; every transaction `IsFinalTx(tx,
nHeight, nLockTimeCutoff)`; if `DeploymentActiveAfter(pindexPrev, HEIGHTINCB)` (`nHeight ≥
227931`) the coinbase's first input `scriptSig` must have `CScript() << nHeight` as a prefix (size
test then `std::equal` over the prefix); `CheckWitnessMalleation(block,
DeploymentActiveAfter(pindexPrev, SEGWIT))` (`nHeight ≥ 481824`, spot 12); `GetBlockWeight(block) ≤
MAX_BLOCK_WEIGHT`.

The Lean: `height := S.nextHeight` (= `headers.length` = tip height + 1); `cutoff := if activeAfter
S.tipHeight .csv then S.mtp else header.time` with `activeAfter prev dep = deploymentHeight dep ≤
prev + 1` and `S.mtp = medianTimePast (timesTo tipHeight)`, the MTP of the tip = `pindexPrev`;
`vtx.all (isFinalTx · height cutoff)`; `!activeAfter S.tipHeight .heightInCB || (heightScript
height).isPrefixOf cb.vin[0].scriptSig` (`isPrefixOf` is the size test plus the prefix equality);
`checkWitnessMalleation b (activeAfter S.tipHeight .segwit)`; `blockWeight b ≤ 4,000,000` with
`blockWeight = stripped*3 + full` = `GetBlockWeight` (serialization: spot 16). Same tests, same
order, same activation heights (227931, 419328, 481824 from `CMainParams`). The `headD` defaults
for the coinbase and its first input are unreachable on the validation path because
`checkBlock` runs first (non-empty `vtx`, first transaction a coinbase with exactly one input);
Core relies on the same precondition (`block.vtx[0]->vin[0]` without a test).

## `IsFinalTx` — `isFinalTx`

Core: `nLockTime == 0 → true`; `nLockTime < (nLockTime < LOCKTIME_THRESHOLD ? nBlockHeight :
nBlockTime) → true` (all compared as `int64_t`); otherwise `true` iff every input has `nSequence ==
SEQUENCE_FINAL` (`0xffffffff`); a transaction with no inputs is final here (vacuous), rejected
elsewhere. The Lean is the same three steps with `Int` comparisons, `LOCKTIME_THRESHOLD =
500,000,000`, `SEQUENCE_FINAL = 0xffffffff`, `vin.all`. Identical. (`nLockTime` is an unbounded
`Nat` in the model, limit L2; Core's `uint32_t` cast to `int64_t` never wraps.)

## `CScript() << nHeight` — `heightScript`

Core `push_int64(n)`: `n = -1` or `1 ≤ n ≤ 16` → the single byte `n + (OP_1 − 1)` = `0x50 + n`;
`n = 0` → `OP_0` (`0x00`); otherwise `*this << CScriptNum::serialize(n)`, a data push with the
smallest push opcode for the length (direct byte below `0x4c`, `PUSHDATA1` to `0xff`, `PUSHDATA2`
to `0xffff`, else `PUSHDATA4`). `CScriptNum::serialize` of a positive number is its little-endian
magnitude with a `0x00` appended when the top bit of the last byte is set.

The Lean: `n = 0 → [0]`; `n ≤ 16 → [0x50 + n]`; else `pushBytes (BitcoinScript.serialize n)`, with
`serialize` the `CScriptNum` encoding (reviewed in the Script mission) and `pushBytes` the same
size ladder. `n` is a `Nat`, so the `−1` case does not arise (heights are non-negative). Identical.
On mainnet BIP34 is enforced only from height 227931, where the push is always `03 xx xx xx`
(three bytes) until height 8,388,608; the small-number branches are still faithful.

Vectors: 19 heights including every encoding boundary (0, 1, 16, 17, 127/128 (sign byte), 255/256,
32767/32768, 65535/65536, 227931, 2^23 − 1 / 2^23, 2^24 − 1 / 2^24, 2^31 − 1); a non-minimal push of
the same number is a different prefix and is rejected, as in Core (byte equality, not numeric).

## Cutoff and activation vectors

Synthetic chains of `n` headers 600 s apart (times from 1.5·10^9): at next height 170 the cutoff
is the block time (lock at time − 1 final, at the block time not final; height lock at 169 final,
at 170 not); at next height 419328 the cutoff is the tip's MTP (= the time of the sixth most
recent block, checked numerically), a lock equal to the MTP fails even though it is below the
block time, and one block earlier (next height 419327) the same lock passes under the
block-time cutoff; `SEQUENCE_FINAL` on every input overrides the lock; BIP34 enforced exactly from
next height 227931 (prefix with trailing bytes, exact, previous height, truncated); witness data
without a commitment rejected at 481824 and at 481823 (the no-witness rule applies either way);
a block of weight exactly 4,000,000 passes and one more byte fails.

## Checks from the guide

- **Order of tests.** Finality, BIP34, witness malleation, weight: the same; verdict-only.
- **Constants.** 500,000,000; 0xffffffff; 227931; 419328; 481824; 4,000,000; `0x50 + n`; `0x4c`,
  `0xff`, `0xffff` push boundaries: all match.
- **Integer semantics.** `Int` comparisons where Core uses `int64_t`; heights as `Nat`; the
  `pindexPrev->nHeight + 1` is `headers.length`, with no subtraction.
- **Defaults.** `headD` for the coinbase/first input unreachable after `checkBlock`; `medianTimePast`
  of an empty window returns 0 but the chain always holds at least the genesis header.
- **Policy vs consensus.** None of `ContextualCheckBlock` is policy; the standardness lock-time
  rules (`IsFinalTx` against `nBestHeight + 1` and `GetAdjustedTime` in the mempool) are not in
  the model, correctly.
